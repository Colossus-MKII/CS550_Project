# 2. SAM 2.1: prompted video segmentation

[Guide index](README.md) · [Previous: YOLO and ByteTrack](01-yolo-and-bytetrack.md) · [Next: SAM-Track and DeAOT](03-sam-track-and-deaot.md)

## The one-sentence explanation

SAM 2.1 can outline a specified object and follow its mask through a video, but our application must decide which objects to introduce and how to manage their identities.

## What the name means

SAM means Segment Anything Model. SAM 2 extends promptable segmentation to images and videos; SAM 2.1 is an updated checkpoint release in that model family. Our required checkpoint is `sam2.1_hiera_tiny.pt`. The official table lists 38.9 million parameters for Tiny and 46 million for Small. These are two sizes of the same family, not two different tasks. Small is downloaded but is not required by our proposal. See the [official SAM 2 repository](https://github.com/facebookresearch/sam2).

The proposal's choice of Tiny is a scope decision, not evidence that it wins on our videos. Published speed numbers from other hardware and protocols are not our end-to-end speed measurements.

## Inputs and outputs

A spatial prompt specifies an object using a point, box, or mask on a particular frame. Video propagation then produces masks for the specified object over other frames. This is different from asking a language model to understand the sentence “find all dogs.”

In the official video interface, the caller supplies an `obj_id` when adding a prompt. Propagation returns frame indices, object IDs, and mask scores/logits. A logit is a numerical mask prediction before converting it into a binary pixel selection. Our implementation must document that conversion. See the [video predictor implementation](https://github.com/facebookresearch/sam2/blob/main/sam2/sam2_video_predictor.py).

Crucially, returning the same numerical ID does not prove the model stayed on the same real object. Track 7 can keep its name while its mask drifts from dog A to dog B. That is an identity error despite the unchanged integer.

## How it works, without the full mathematics

The main components are:

- An image encoder, using a Hiera backbone, turns the current frame into visual features at multiple scales.
- A prompt encoder represents the spatial selection.
- Memory attention relates current features to stored information about the target.
- A mask decoder predicts the current outline.
- A memory encoder stores information from frames and predicted masks for subsequent processing.

This is a learned temporal segmentation system, not simply a box moving at a constant velocity. The model also has an object-presence prediction mechanism. However, predicted absence and application-level track retirement are different decisions. See the [SAM 2 paper, model section](https://arxiv.org/html/2408.00714v2#S4).

Video memory is temporary inference state. Updating it does not update the pretrained neural-network weights.

## How our proposal makes it automatic

The following is **our planned integration**, not an off-the-shelf guarantee:

1. At a discovery frame, run YOLO11s-seg and keep candidate boxes for our target categories. B0 uses pretrained weights; B1 uses the same adapted checkpoint as A1. Weights remain fixed throughout each inference run.
2. Propagate existing SAM objects to that frame and obtain their current mask bounding boxes.
3. Match detections one-to-one to eligible same-category tracks using box IoU.
4. Use matched detections for prompt refresh under a fixed rule. Create new IDs for accepted unmatched detections.
5. Continue forward propagation. Handle empty masks, missing detections, and track retirement according to explicit rules.

The first frame is a special case: there are no existing tracks to match. The wrapper stores the category associated with each ID. SAM receives the spatial prompt; it is not itself responsible for labeling the result `dog` or `car`.

In this experiment, YOLO's mask is not the SAM initialization input: the proposal specifies a **box prompt**. Switching to detector-mask prompts would be a different configuration and should be reported separately. SAM 2.1 remains frozen in both B0 and B1; the adaptation experiment changes the detector, not SAM's weights.

### Example: a new dog enters later

Imagine dog A is introduced at frame 0, while dog B enters at frame 13. If discovery runs at frames 0, 10, 20, and so on, B may not be introduced until frame 20. Its earlier annotated appearances still count as misses. A larger discovery interval might save detector work but hurt recall.

If A disappears and returns, our matching/retirement code must decide whether to recover the old identity or start a new one. The phrase “SAM tracks objects” does not specify this full lifecycle.

## Why this is not a pure SAM-versus-YOLO test

Pipeline B includes YOLO discovery, SAM segmentation, and our own association logic. Its results depend on all three. It also shares the detector's category vocabulary and discovery errors. Even if SAM could segment an unfamiliar object when prompted, our detector-gated system will not automatically become open-vocabulary.

An improvement would support a claim about **this complete pipeline under this protocol**, not that every gain came from the segmentation backbone. A missed first detection, duplicate new ID, or bad refresh can obscure otherwise good mask propagation.

## Forward-only processing needs deliberate implementation

SAM 2 can condition on prompts from later frames. Our forward-only experiment must not. Add prompts chronologically and verify that future prompts cannot influence earlier scored predictions; forward iteration is insufficient if future prompts were registered already. See the [paper's description of prompted-frame memory](https://arxiv.org/html/2408.00714v2#S4).

Loading a video into memory is not itself future-information leakage. Using future prompts or future-derived predictions to affect an earlier scored frame is the issue. Separately, loading all frames at once can affect memory and timing.

## GPU use and training

Inference memory includes weights, features, masks, object state, and frame storage. A 156 MB checkpoint does not imply a 156 MB GPU footprint. The official predictor offers CPU offloading for video frames and inference state; these settings can trade GPU memory for other costs and must be recorded. See its [`init_state` implementation](https://github.com/facebookresearch/sam2/blob/main/sam2/sam2_video_predictor.py).

Our next feasibility check should use one GPU, Tiny, a short validation clip, and a small number of objects, then increase clip length and object count while measuring memory. The available RTX A4000/RTX 3080 devices are candidates for this pilot, not proof that every configuration fits. No SAM fine-tuning is required. Official [training instructions](https://github.com/facebookresearch/sam2/blob/main/training/README.md) describe a separate workflow; inference success would not establish training feasibility.

## Questions to ask while reviewing the proposal

Can we explain where every prompt comes from? What happens to late arrivals? How are duplicate IDs avoided? Can a refresh switch a track to the wrong nearby object? How do we emit no mask for an absent target? These integration questions matter at least as much as choosing Tiny versus Small.
